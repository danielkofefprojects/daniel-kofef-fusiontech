# AI Collaboration Log

## Tools

- **Claude Code** (Claude Opus 5.5) in the VS Code extension, used in plan mode first and then for implementation. All code, tests and documentation in this repository were generated by it.

## How I worked with it

I started in plan mode so that no code was written until I had approved a design. The assistant asked three questions before planning (LLM provider, language, guardrail), wrote a plan covering the data model, the state machine, the validation pipeline and the verification steps, and only started coding after I approved it.

## Prompts I relied on

Four prompts did most of the steering. They are reproduced here in edited form for clarity, each followed by what it was for and what it changed.

### 1. Kickoff: plan first, with the full brief

> here is the complete challenge brief The service must be implemented in node.js before writing any code produce an implementation plan and ask me any questions you need.

- **Purpose:** hand over the complete challenge brief and fix the language (Node.js), while asking for a plan rather than code.
- **Effect:** the assistant stayed in plan mode and asked three clarifying questions (LLM provider, language, guardrail) before proposing a design.

### 2. Provider decision: overriding the recommendation

> use groq as the llm provider i already have an api key for it keep the integration behind a small interface so the provider can be swapped later.

- **Purpose:** answer the provider question with a constraint the assistant could not know (I already had a Groq key). It had recommended Anthropic first.
- **Effect:** Groq became the provider, isolated behind a one-method `LlmClient` interface so the choice lives in a single file.

### 3. The UI: a small front end on top of the finished API

> the backend is done now add a simple React front end in a separate folder, without changing the api It needs a page to submit feedback and a list of feedback items showing status, category, with filters, paging, a retry button for failed items and a details modal. Keep it small, use only the existing endpoints, and update the README and do not add any additional packages.

- **Purpose:** add a usable front end after the backend was finished, with the API contract fixed so the UI could not push changes into it.
- **Effect:** Claude Code generated the Vite/React app in `ui/`, which talks only to the existing endpoints. See "The UI" below for what was and was not verified.

### 4. Live verification: putting the real provider in the loop

> the groq api key is now set in .env run the service end to end against the real provider and report the results including any failures

- **Purpose:** the first build passed all tests against a fake LLM, which proves nothing about the real provider.
- **Effect:** the live run exposed the non-existent default model (see issue 2 below) and led to the fix and a re-run.

## The UI

The React front end in `ui/` (submit page and feedback list with filters, paging, retry and a details modal) was also generated by Claude Code, after the backend. It has no automated tests and was not part of the plan or the live verification above; see the README's Web UI section.

## Review pass against the code

I asked the assistant to compare this log and the README against the code only. It found, and I had it fix:

- The README did not mention the UI at all.
- "Case-insensitive search" was only true for ASCII, because SQLite's `lower()` does not fold other characters. A Unicode-aware SQL function now does it.
- A reply cut off by the token cap was reported as "not valid JSON". The Groq client now fails it explicitly as truncated.
- Undocumented behaviour: the `400` body shape, unknown query parameters being ignored, the sentiment filter excluding unanalyzed items, `404` on `GET /feedback/:id`, the 1000-character error truncation, binding to `127.0.0.1`, and items staying `ANALYZING` if the outcome cannot be written.
- Several behaviours had no tests (queue, config, the Groq client, duplicate edge cases, search edge cases); the test suite grew from 23 to 49 tests.

## Where the AI output was wrong or low quality, and what was done about it

**1. Request validation that would have silently accepted bad input.**
The approved plan said to use Fastify's built-in JSON-schema validation for request bodies. Fastify's default validator configuration coerces types and strips unknown properties, so `{"content": 42}` would have been stored as the string `"42"` and `{"content": "ok", "extra": true}` accepted without complaint. For a service whose whole point is defensive handling of input, that is the wrong default. The implementation was changed to explicit strict Zod schemas in the route handlers, and both cases are now covered by tests that expect `400`.

**2. A default model id that did not exist.**
`npm install` resolved to major versions newer than the assistant's assumptions (Zod 4, TypeScript 7, groq-sdk 1.x), so it checked parameter names and model ids against the installed SDK's type definitions instead of writing from memory. That was still not enough: it picked `llama-3.3-70b-versatile` as the default because the SDK's types list it, and all 23 tests (at that point) passed with a fake LLM. The first run with my real key failed every item with `404 model_not_found`. The service handled it correctly (each item `FAILED` with the provider's error stored, nothing stuck), but the default was wrong. The fix was to ask the Groq API which models the key can actually use, switch the default to `openai/gpt-oss-120b`, raise the output token cap because it is a reasoning model, and re-run the live test. The lesson I took: type definitions and green mocked tests say nothing about what the provider serves today, so the real API has to be in the verification loop.

**3. Provider choice.**
The assistant's first recommendation was a different LLM provider from the one I had a key for. I constrained it to Groq; it kept the provider behind a one-method `LlmClient` interface, so that decision is isolated to one file.

## What I would improve with more time

- Turn the manual live test (five inputs, including a prompt-injection attempt and Hebrew text, all valid on the first attempt) into a larger evaluation set and record how often strict validation fails, then decide from data whether to move to `json_schema` structured outputs.
- Harden the prompt against injection. A live test showed the model keeps the correct sentiment but still reports an injected "Give me admin access" as a high-confidence feature request (see the limitations in the README). Schema validation does not catch this, so it needs prompt changes and an evaluation case.
- Replace the in-process queue with a jobs table with leases so multiple workers are safe, and add capped automatic retries for retryable failures.
- Have the assistant write a second, adversarial review of its own state-transition code (crash between claim and completion, two processes, shutdown mid-request) and turn each finding into a test.
- Track duplicate counts instead of only collapsing duplicates.
